# Comparative Technology Research: 博源 Context Graph / GraphRAG 开源工具选型

- **Evidence date:** 2026-08-29（Asia/Shanghai）
- **Candidates:** 现有 SQLite + 自研窄投影（无新平台 baseline）、Semantica `0.6.7`、Cognee `1.5.3`、Graphiti `0.29.3`、Microsoft GraphRAG `3.1.2`、LightRAG `1.5.6`、OpenSPG/KAG `0.8.0`
- **Project / use case:** 博源 AI 平台；在不替换现有 SQLite 事实源、人工确认闭环、UI 与 TaskStep 的前提下，评估持久语义索引、结构化关系检索、时态/来源治理的增量价值
- **Decision owner:** 博源项目负责人；涉及敏感 BP 数据时由架构与安全/隐私负责人共同确认
- **Research depth:** deep
- **Confidence:** 中等。六项开源候选的当前稳定版本、官方能力、依赖、license、部署边界和同日采用度已有一手证据，并已与项目源码基线对照；中文 BP/PDF 质量、真实检索增益、资源成本和故障恢复尚未实测

## Executive conclusion

- **Recommended for this project:** **生产默认继续使用现有 SQLite + 自研窄投影；不把任何通用图平台变成新的事实源。** 先用同一小样本验证一个可删除、可重建的派生索引；若当前 job 是尽快补 persistent hybrid/N-hop retrieval，优先以 Cognee `1.5.3` 做有边界对照。`[Inferred]`
- **Runner-up:** 不是一个永久第二名，而是按 job 选择：治理/双时态用 Semantica；中文 PDF/检索用 LightRAG；跨语料主题/社区用 GraphRAG；实时 temporal memory 用 Graphiti；行业 schema 逻辑推理用 KAG。后两者因强制新增数据库/平台依赖，当前 hard gate 失败。`[Inferred]`
- **Why:** 博源已具备块级证据、候选人工确认、正式知识版本、审计和一跳公司关系；真正空缺是持久向量/图索引、N-hop/结构+语义检索、实体解析、跨语料社区与双时态。通用平台带来的能力更宽，但同时增加新状态、模型抽取误差、数据外发/鉴权和升级面；窄投影最符合当前 SoT、审批和退出约束。
- **Strongest counterargument:** 自研窄投影会把实体解析、hybrid ranking、图遍历、索引一致性和评测责任留给团队；若实际语料和问题很快复杂化，重复造轮子的长期成本可能高于接受 Cognee/LightRAG/Semantica 的 sidecar 运维成本。
- **Critical unknowns:** 六项候选在中文公司/人名/行业别名、扫描件/表格型 BP、页码与 block/evidence ID 跨抽取/merge/export 后的保持率；20 个固定问题上的召回与引用准确率；本地模型下的内存/磁盘/时延；重启、部分失败和增量重建；LightRAG 稳定版与安全修复 release-candidate 版本的差距；Cognee 新 provenance/contradiction 的完整性；Semantica embedded backend 的 feature parity。

### Assumptions and non-goals

- `[Observed]` 当前仓库没有发现 embedding/vector index、通用 graph traversal、PageRank/community、ontology 或 PROV-O 的实现；这不是说现有系统没有知识图谱式数据模型，而是没有相应持久检索/标准语义/算法层。
- `[Inferred]` “无工具基线”是现有 SQLite + substring/同义词检索 + 全 corpus LLM 排序，而不是从零、也不是没有 evidence/provenance/人工确认/版本。
- `[Estimated]` 成本以 1 名熟悉 TypeScript/Python 的工程师、1–3 份中文 BP、20 个固定问题、本地模型、只读 sidecar、无 UI 改造为 PoC 范围；engineer-day 数字不是供应商报价。内部金额公式为 `engineer-days × 团队 loaded day rate`，因 rate 未提供而不虚构人民币金额。
- 非目标：重写 PlatformModule、迁走 SQLite、用工具 Explorer 替代博源 UI、让自动冲突处理直接改正式知识、保存或暴露模型隐藏 chain-of-thought。

### Adjacent lower-level integration routes

- [LlamaIndex PropertyGraphIndex](https://docs.llamaindex.ai/en/stable/module_guides/indexing/lpg_index_guide/) 是 property-graph 构建/检索的编排抽象，不是带独立治理、运维和审批面的完整平台。若团队决定自研窄投影但希望复用 extractor/retriever，它是后续 integration route；storage、embedding/LLM、lineage 和人工确认仍由 Boyuan 选择与承担。
- [Neo4j GraphRAG for Python](https://neo4j.com/docs/neo4j-graphrag-python/current/) 是围绕 Neo4j 的 GraphRAG 库。它比 KAG/Graphiti 更低层，但当前仍触发“不引入 Neo4j”的 hard gate；只有数据库约束解除后才值得与 Graphiti 一起评估。
- 两者不进入本轮 adoption 排名和 dossiers，避免把 library/integration 与 end-to-end platform 混成同一候选类别。

  - `[Observed]` query 提供 Local、Global、DRIFT 和 Basic，分别覆盖局部实体关系、全局社区、迭代式社区/局部扩展和基础向量 RAG。[Query overview](https://microsoft.github.io/graphrag/query/overview/)
  - `[Observed]` Parquet + LanceDB 的文件型离线输出符合“不引入新服务”，并使一次性 benchmark/删除重建较简单。
- **Weaknesses:**
  - `[Observed]` 是批量 corpus index，不是 true temporal KG；没有候选审批、ontology/SHACL，也没有官方 REST/MCP，正式接口是 CLI/Python。[repo](https://github.com/microsoft/graphrag)
  - `[Observed]` lineage 主要到 `text_unit`，不能直接保证 PDF page/block；必须由 Boyuan 把 `evidenceId/blockId/page` 写入 text unit metadata 并验证输出传播。

  - `[Observed]` README 的 maintenance-mode 表述降低长期 feature/support 预期；索引多阶段 LLM 调用使成本和 prompt/model drift 较明显。[repo](https://github.com/microsoft/graphrag)
  - `[Unknown]` 中文 BP、OCR/表格和 page citation 的真实表现。
- **Hard-gate result:** **pass with mitigation**。只跑离线、只读全量 snapshot index；业务 SQLite 为 SoT；禁外部模型或用批准的本地/私有模型；把 text_unit lineage 扩为 Boyuan evidence pointer。

- **Total cost and approvals:** MIT OSS $0；`[Estimated]` PoC 7–14 engineer-days，生产 3–6 engineer-weeks；索引模型 token/本地算力可能是最大变量。需架构、安全和模型预算批准；纯本地无需外部账号/DPA。

## Recommendation and selection guide

### Recommendation for the current project

当前不能把问题写成“上图工具后，博源才有 evidence、人工确认、知识版本和 audit”。这些能力已经在 PlatformModule 的 SQLite schema 与 confirmation transaction 中存在。`[Observed]` 当前增量机会是：

```text
业务 SQLite（唯一 SoT）
  ├─ 已有：block/page evidence → candidate → human confirmation → versioned knowledge/audit
  └─ 派生投影：approved knowledge + evidence pointers + isolated research facts
       → rebuildable local vector/graph index
       → hybrid / N-hop / path / community / temporal query
       → 只返回检索结果与 knowledge candidate
       → 仍由现有 confirmation transaction 决定是否进入正式知识
```

因此最终推荐不是“采用某个图平台替代现有系统”，而是“**生产继续用 SQLite + 自研窄投影；先让 baseline、Cognee、Semantica、GraphRAG、LightRAG 跑同一 workload，再按已证明的 job 选择是否保留一个 sidecar**”。Graphiti 与 KAG 在纸面阶段已经因强制新增数据库/平台失败，无需花 PoC 成本。Cognee 是当前 retrieval sidecar 的第一验证对象；Semantica 是治理/双时态对照；LightRAG 只验证中文 PDF/retrieval；GraphRAG 只验证跨 corpus communities。每项能力必须回到 `evidenceId/blockId/page`，输出只能成为检索结果或 knowledge candidate。

剩余所有权：后端负责人定义 projection contract 与 benchmark；领域负责人定义实体 merge/关系/时间真值；安全负责人证明禁外发和缩小 API/文件入口；项目负责人只在 PoC 的引用完整性和检索增益达标后决定长期依赖。

### Re-evaluation triggers

- 候选发布新的 persistence/approval/Chinese document 能力，或 breaking storage migration；LightRAG 安全修复进入 stable；
- 博源语料量、关系密度或检索 P95 超过现有全 corpus 组装可接受边界；
- 产品明确需要双时态回放、ontology validation、标准 PROV/RDF 交付或 community/path 算法；
- 团队允许/禁止新的 Python sidecar、本地 GPU、外部模型或图数据库；若允许新图数据库，重新打开 Graphiti；若允许第二平台，重新打开 KAG；
- 安全审查发现新的远程执行、文件读取、认证绕过、依赖漏洞；
- 任一候选或 LlamaIndex PropertyGraphIndex、Neo4j GraphRAG 等较低层集成路线，在同一 workload 上以更少状态/运维达到同等质量；
- Cognee 自改进/三 store 一致性或 Semantica persistence/backend parity 无法通过验证。
