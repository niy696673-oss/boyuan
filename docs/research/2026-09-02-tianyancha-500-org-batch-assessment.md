# 天眼查 500 家机构批量获取评估

> 调研日期：2026-09-02\
> 结论适用范围：博源平台一次性或周期性补充机构/企业基础档案。本文只使用天眼查与中国政府官方一手资料；耗时数字除官方频控外均为容量规划假设，不是天眼查 SLA 或实测承诺。

## 一句话结论

**500 家基础工商信息在技术上处理得过来，但应当走天眼查正式开放 API，不应抓取天眼查网页。** 如果 500 家已有准确企业名称或统一社会信用代码，按一家一次“企业基本信息”调用估算是 500 次；如果要先搜索消歧再取详情，则约 1,000 次。天眼查公开协议写明默认调用上限为每分钟 1,000 次，因此 500 家不是吞吐瓶颈，真正需要先确认的是账号接口权限、套餐次数、最终使用主体、字段范围和合同授权。

“处理得过来”不等于“可以把 500 家都做完整外部深度研究”。只拉基础工商信息可按分钟级批处理；若每家还要搜索外部资料、调用 OpenCode 生成研究候选并人工审核，工作量会扩大到小时级，人工确认通常成为主瓶颈。

## 1. 先明确“机构信息”的口径

至少有两个不同范围，接口量和成本差异很大：

1. **法律主体基础档案**：企业名称、状态、统一社会信用代码、注册资本、法定代表人、成立日期、注册地址、经营范围、行业等。
2. **投资机构业务画像**：管理团队、基金、投资事件、投资偏好、被投项目、募资动态等。

天眼查开放平台的接口目录显示工商信息、投资机构、私募基金等多个独立类别；基础信息不等于完整投资机构画像。公开目录显示“投资机构”有 10 项接口、“私募基金”有 7 项接口，但没有在公开文档中核实到一个可以把任意 500 个机构名称放进单次请求的批量接口。[天眼查开放平台接口目录](https://open.tianyancha.com/api_list)

因此，下午讨论时最好把需求先切成：

- 第一阶段：500 家法律主体基础档案；
- 第二阶段：其中重点机构的投资画像和外部研究。

## 2. 官方 API 能力与公开限制

### 2.1 可以确认的接口能力

| 场景 | 官方公开能力 | 调用形态与公开单价 |
| --- | --- | --- |
| 按企业名发现主体 | “搜索”接口可按关键词返回企业列表，包含名称/ID、成立日期、经营状态、统一社会信用代码等；`pageSize` 默认 20、最大 20 | `GET /services/open/search/2.0`，Authorization token；页面显示 ¥0.01/次。[官方接口 816](https://open.tianyancha.com/open/816) |
| 获取基础工商信息 | “获取企业基本信息”支持企业名称、公司 ID、注册号或统一社会信用代码等关键词 | `GET /services/v4/open/baseinfo`，Authorization token；页面显示 ¥0.15/次。[官方接口 362](https://open.tianyancha.com/open/362) |
| 基础信息含主要人员 | 可按名称或 ID 获取企业基础信息及主要人员 | `GET /services/v4/open/baseinfoV3`；页面显示 ¥0.25/次。[官方接口 365](https://open.tianyancha.com/open/365) |
| 按行业、区域发现公司 | 可按关键词、国标行业码和行政区划获取企业列表，返回名称/ID、经营状态、信用代码、法定代表人等 | `GET /services/v4/open/searchV3`；页面显示 ¥0.2/次。[官方接口 776](https://open.tianyancha.com/open/776) |
| 按信用代码定位 | 可根据信用代码、组织机构代码或注册号获取公司信息 | `GET /services/v4/open/getCompanyByCode`；页面显示 ¥0.25/次。[官方接口 736](https://open.tianyancha.com/open/736) |

这些公开接口足以支持“名称/信用代码输入 → 主体匹配 → 基础档案补全”。搜索接口一次最多返回 20 个候选，适合发现和消歧；它不是“500 个指定名称一次提交”的批量入参。[官方搜索接口](https://open.tianyancha.com/open/816)

### 2.2 调用、套餐与权限边界

天眼查 API 用户协议目前公开写明：

- 支持预充值和包年包量两种线上交易模式；包年套餐次数用尽时服务提前届满；
- 查询/调用频次每分钟上限默认为 1,000 次；
- API 数据仅限用户内部使用，不得销售、提供或许可给包括关联企业、客户、供应商在内的其他主体；
- 数据应在中国大陆范围内存储及/或使用，不得向境外传输；投融资属于协议列出的合理用途之一，但超出公开用途范围时应向天眼查说明；
- 接口、字段和用量计算规则可能调整，以实际接口页面为准。

来源：[天眼查 API 用户协议，2025-04-01 生效](https://open.tianyancha.com/property/protocol)

公开接口错误码还包括“访问频率过快”“无权限访问此 API”“余额不足”“剩余次数不足”“此 IP 无权限访问此 API”等，说明实际运行除了默认总频控外，还受购买权限、余额/套餐和 IP 设置约束。[官方接口错误码示例](https://open.tianyancha.com/open/776)

### 2.3 本次无法从公开材料确认的内容

- 当前项目账号是否已购买所需接口、剩余次数和实际单账号/单接口限流值；公开协议只说**默认**每分钟 1,000 次。
- 天眼查是否能为本项目提供专用“500 家名单批量文件”或离线数据交付；公开页面没有足够材料证明，应向官方商务书面确认。
- 官方服务的平均、P95、P99 延迟和可用性 SLA。
- 失败调用、空结果、重试是否计费，以及具体套餐折扣。
- 投资机构 10 项接口的完整字段权限、接口组合和商务价格。
- 如果博源替客户建设并运营平台，谁应作为天眼查 API 合同与账号主体，以及结果能否展示给客户用户。由于公开协议限制向客户提供数据，这一项必须取得天眼查书面授权，不能只凭技术可行性上线。

## 3. 为什么不建议“网页抓取”

这里必须区分两个方案：

- **正式 API 调用**：平台公开提供、token 鉴权、按次或按套餐计费，有明确字段、错误码和频控，是可控集成路径。
- **自动化抓网页**：天眼查 API 用户协议明确禁止在正常 API 使用方式之外通过机器抓取、复制、镜像获取网站信息，并同时禁止恶意或非人为的连续频繁查询及不合理大批量获取；平台可采取封号、封 IP、暂停服务等措施。[天眼查 API 用户协议](https://open.tianyancha.com/property/protocol)

因此，“在天眼查里面抓取”如果指网页爬虫，答案应当是**不按这个方案承诺**；如果指官方 API，则 500 家的技术规模可控。

即使数据是公开信息，也不意味着可以无限制处理其中的自然人信息。《个人信息保护法》要求处理个人信息遵循合法、正当、必要、最小范围原则；对已经合法公开的个人信息也只能在合理范围内处理，若对个人权益有重大影响仍需取得同意。[国家市场监督管理总局公布的《个人信息保护法》](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)、[中央网信办公布的第二十七条](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)

《数据安全法》还要求数据收集采用合法、正当方式，建立全流程安全管理制度并采取必要技术措施。[中央网信办公布的《数据安全法》](https://www.cac.gov.cn/2021-06/11/c_1624994566919140.htm)

## 4. 500 家的成本和吞吐估算

### 4.1 公开页面单价下的最低接口成本

以下仅按 2026-09-02 官方公开页面单价机械计算，不含套餐折扣、其他字段接口、失败/重试和开发成本：

| 口径 | 调用数 | 公开页面价推算 |
| --- | ---: | ---: |
| 已有准确名称/ID/信用代码，只取基础信息 | 500 次基本信息 | 500 × ¥0.15 = **¥75** |
| 名称先搜索消歧，再取基础信息 | 500 次搜索 + 500 次基本信息 | 500 × (¥0.01 + ¥0.15) = **¥80** |
| 直接取基础信息含主要人员 | 500 次 | 500 × ¥0.25 = **¥125** |
| 先搜索，再取基础信息含主要人员 | 1,000 次 | 500 × (¥0.01 + ¥0.25) = **¥130** |

单价来源：[搜索接口](https://open.tianyancha.com/open/816)、[企业基本信息](https://open.tianyancha.com/open/362)、[企业基本信息含主要人员](https://open.tianyancha.com/open/365)。实际结算必须以账号套餐和正式报价为准。

### 4.2 可计算的耗时公式

定义：

- `N`：机构数，本题为 500；
- `s`：每家所需 API 次数，直接详情为 1，搜索再详情为 2；
- `R`：账号允许调用频率（次/分钟），协议公开默认上限 1,000，但实际值需账号验证；
- `L`：单次 API 的平均有效耗时（秒，需试跑测量）；
- `C`：并发数；
- `T_retry`：限流、超时和临时失败的退避重试时间；
- `T_write`：校验、SQLite 入库、审计写入时间。

粗略墙钟时间公式：

```text
T_total（分钟）≈ max(N × s / R, N × s × L / (60 × C))
                  + T_retry + T_write
```

官方只公开 `R` 的默认上限，没有公开 `L` 或 SLA，所以不能直接承诺精确完成分钟数。用于容量规划，可以先用 `L = 1–3 秒` 做保守试算（这是本项目假设，不是官方性能数据）：

| 场景 | 试算参数 | 公式结果 | 建议对外预算 |
| --- | --- | ---: | ---: |
| 准确标识，只取一次基础详情 | `s=1, C=1` | 约 8.3–25 分钟 | **10–30 分钟** |
| 准确标识，4 并发 | `s=1, C=4` | 约 2.1–6.3 分钟 | **3–10 分钟** |
| 名称搜索 + 基础详情，4 并发 | `s=2, C=4` | 约 4.2–12.5 分钟 | **5–20 分钟** |

以上区间的前提是账号允许该调用模式、响应体不大、失败率低，且只做结构化校验和 SQLite 写入。上线承诺必须用 10 家试跑测得的 `L`、错误率和真实限流重算。

### 4.3 如果连带做外部深度研究

博源当前公司研究不是一个简单 HTTP 请求，而是“主体解析 → 读取正式知识 → 规划搜索 → 外部搜索 → OpenCode 分析 → 生成候选”的六步异步流程（见 `server/research-platform/platform-module.ts` 中的 `RESEARCH_STEPS`）。因此不能把天眼查 500 次基础信息调用的时间等同于 500 家完整研究时间。

在没有线上基准前，可仅做容量情景：若每家外部搜索与 AI 分析合计占用 30–180 秒，4 并发处理 500 家约为 **1.0–6.3 小时**；当前默认 1 并发则约为 **4.2–25 小时**。这个区间不是性能承诺，还没有计入 Exa/OpenCode 各自的配额、重试和人工确认。

更重要的是，深度研究会为每家生成多条待确认知识。若每家只产生 5 条候选，500 家也有 2,500 条待人工审核；因此应该只给筛选后的重点机构做深研，而不是默认对 500 家全量执行。

## 5. 与博源当前实现的适配判断

现有实现已有承接批处理所需的大部分骨架：

- `PlatformWorker` 是异步轮询任务，默认每批 10 个步骤、并发 1，允许配置到并发 8（`server/research-platform/platform-worker.ts`、`worker-config.ts`）。
- 任务步骤带 lease，租约过期可以重新排队；步骤领取在 SQLite 中以条件更新完成（`platform-module.ts` 的 `#recoverExpiredSteps`、`#claimNextStep`）。
- 失败任务可以人工重试，渠道附件有幂等接入记录。
- 外部事实先形成带证据的知识候选；没有证据不能确认，确认写入版本化正式知识和审计记录（`platform-module.ts` 的 `#validateCandidateDecision`、`#applyCandidateDecision`）。

因此，**SQLite 存 500 家结构化档案没有容量问题；需要补的是天眼查 provider adapter 和面向批量补全的任务状态，而不是更换数据库。** 但现有 worker 当前面向研究步骤，默认并发只有 1；500 家基础档案不应逐家启动完整 OpenCode 深研会话，应新增轻量的 `institution_enrichment` 批任务，完成主体匹配、官方 API 拉取、字段映射和候选入库。

## 6. 推荐实施方式

### 6.1 先做 10 家试跑

选择具有代表性的 10 家：

- 6 家名称唯一、状态正常的机构；
- 2 家存在同名/简称/曾用名的机构；
- 1 家非企业主体；
- 1 家预期无结果或已注销的机构。

试跑必须记录：每个接口实际延迟、错误码、计费扣次、字段缺失率、名称匹配准确率、响应更新时间、是否包含个人信息以及单家产生的候选数量。只有 10 家试跑通过后再放 500 家。

### 6.2 500 家批处理控制

1. **输入去重和稳定标识**：优先统一社会信用代码，其次天眼查 company ID，最后才用公司全称；简称和模糊名称必须进入人工主体确认。
2. **断点续跑**：每家保存 `queued/running/succeeded/no_result/retryable_failed/permanent_failed/pending_confirmation` 状态、attempt、nextRetryAt 和最后错误码；重启后从非终态继续。
3. **保守限流**：首轮建议从 2–4 并发、120–240 次/分钟开始，这是工程建议而非官方限制；根据 10 家试跑和账号实际限制调整，绝不把公开的每分钟 1,000 次上限当成目标吞吐。
4. **分类重试**：只对网络超时、5xx、`300001` 和 `300004` 等临时错误做指数退避加随机抖动；对无权限、余额/次数不足、参数错误、IP 无权限等错误立即停止对应批次并告警，避免无效扣次。
5. **幂等**：使用 `provider + endpoint + 稳定主体 ID + 字段版本/采集日期` 形成请求与写入幂等键；重复执行只能更新同一批次结果，不能重复创建正式知识。
6. **候选而非正式知识**：天眼查响应保存为来源快照和字段候选，带 `retrievedAt`、endpoint、响应哈希、来源类型及账号合同版本；未经人工确认不覆盖现有正式知识。
7. **证据与审计**：保存原始响应或可验证摘要、字段映射结果、请求 ID、错误码、重试次数、操作者/批次 ID；任何确认、修改和拒绝都进入现有审计记录。
8. **分层研究**：500 家只做基础档案；按规则筛出例如 30 家重点机构，再进入 Exa/OpenCode 外部研究和人工确认队列。

### 6.3 建议验收口径

- 10 家试跑能够从中断点恢复，重复运行不产生重复实体或正式知识；
- 每一家都有明确终态和可追溯错误，不允许“静默漏数”；
- 名称歧义、空结果、权限不足与限流被分别处理；
- 天眼查字段和平台既有正式知识冲突时进入冲突候选，不自动覆盖；
- 500 家批次可以暂停、继续、取消和导出结果汇总；
- 合同主体、内部使用范围、存储地域和个人信息最小化经过业务/法务确认。

## 7. 建议现场回复

可以直接回复：

> 如果说的是通过天眼查正式 API 补齐 500 家机构的基础工商信息，量级上完全处理得过来。已有准确企业名或信用代码时大约 500 次调用；需要先搜索消歧时约 1,000 次。天眼查公开协议的默认上限是每分钟 1,000 次，但实际还要看我们账号购买的接口、套餐次数和限流，所以我不会按理论上限直接跑。
>
> 我建议先拿 10 家做真实试跑，确认字段、命中率、耗时、扣费和授权边界，再按异步队列分批跑 500 家，支持断点续跑、限流、重试、幂等和审计。只拉基础档案预计是分钟级；如果 500 家还要逐家做外部搜索、AI 深度分析和人工确认，那是另一档工作量，应先筛重点机构。另一个前提是走官方 API，不做网页爬虫，账号和数据给谁使用也要让天眼查书面确认。
